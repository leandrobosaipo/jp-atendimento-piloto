# Individual domain permissions

The operational core starts in maintenance. The owner assigns `reply` to a reviewed reply graph and `registration` to the post-delivery contact graph. Only the reply execution node can submit an appointment effect. Only the registration update node can submit a contact effect. Each write requires an unexpired root-issued grant and a native intent for that exact admitted execution. The execution must retain its own forced preflight for the reply role.

The owner places write grants under `ops-config/grants/<key>.json`. `effect_guard.mjs` exports the digest and domain key functions used by both sides of the socket. The key covers the role, task, original event, operation and affected appointment or selected slot. It survives workflow retries and epoch changes. Permits carry the epoch, workflow, node, client, phone, source, task, operation, reference, approved actor, approval timestamp, expiry, target and payload digest. Their maximum lifetime is five minutes. Native creation carries a new UUID in its note; only that UUID is excluded from the approved digest. The native template requires reminders and notifications disabled.

Calendar reads, per-contact official data and independent contact-name cache reads use separate files under `ops-config/read-grants`. The key is the digest of the action followed by role, workflow, node, original event, client, phone, and task (calendar) or request ID (contacts). Calendar permissions explicitly enumerate the queried day and professional. The bridge projects returned calendar rows to the approved customer.

The host keeps an independent durable intent before invoking the provider. Existing intent, crash, timeout, lost response or failed domain readback requires reconciliation by a person. A new grant does not erase that marker. An HTTP success requires the native consumer's subsequent readback. In the contact flow an Evolution cache match remains unverified until the existing separate human web/device evidence.

A new booking or move needs its own permission and the companion `confirm_created` permission for the chosen slot before entering the native write stage. The latter is usable only if the recorded native result identifies the actual appointment and the saved task readback matches the person, service, professional and time. Missing grants hold the task before an attempt. A declined, already-used or uncertain attempt cannot be recycled.

For an authorized cutover the operator provides the appropriate owned epoch and root grants, the current reader generation and a per-operation host policy under `/etc/jp-task-effects/mode.json`. Its default `mode` is `disabled`. Only `official` mode in an owned epoch can reach the fixed official agenda paths. The reply-specific feature switch in the root-owned role config applies to confirming, creating and moving a visit. The native general agenda switch stays disabled. Cancellation, campaign writes and other appointment workflows have no permission here.

Contact updates additionally need the dedicated authenticated adapter origin, credential, exact instance, native contact pilot permit and fresh human baseline. The per-contact native config is private and is automatically paused before requesting the operation. A failed or outdated identity, replacement name, source event, capability, human proof or destination retains the task. This bridge accepts one native contact attempt. An exception permitting a second write requires separate review and is held by this release.
